# Question-To-Quiz: самостоятельный план backend до frontend

Дата плана: 13 октября 2026 года.
Автор проекта: Huseyn. Основной язык: Go. Модуль: qtp.
Режим работы: примерно 20 часов в неделю.
Общая цель проекта: рабочий MVP к 1 февраля 2027 года.
Граница этого документа: законченный backend, документация API и готовая среда для начала frontend. Реализация самого frontend здесь не расписана.

Этот план — рабочий маршрут, а не обещание точной даты. Оценки включают написание кода, чтение документации и ручные проверки. Если новая тема займёт больше времени, сдвигай этапы, а не пропускай проверку доступа, транзакции и сохранение данных.

## Как пользоваться планом

1. Прочитай разделы 0–3, чтобы понимать целую систему.
2. Начни с первого незаконченного шага, а не с начала проекта.
3. Работай над одной законченной возможностью за раз.
4. Закрывай шаг только после его проверки, а не после создания файла.
5. После рабочего результата делай отдельный git commit.
6. Не переписывай уже работающий код ради красоты, если он не мешает следующему шагу.
7. Если застрял, сначала воспроизведи проблему и найди конкретный запрос, ошибку или условие. Затем используй документацию.
8. Названия методов ниже — ориентир. Не переименовывай весь существующий проект ради совпадения с документом.

Готовых реализаций функций и SQL-миграций в этом плане нет. Здесь описано, что написать и как самостоятельно проверить результат.

## 1. Границы первой версии

### Обязательно до frontend

1. Пользователь управляет своими банками вопросов.
2. Импортирует поддерживаемый текстовый DOCX.
3. Видит извлечённые вопросы и найденные проблемы.
4. Сохраняет вопросы в PostgreSQL.
5. Создаёт quiz из выбранного количества случайных вопросов банка.
6. При желании перемешивает варианты.
7. Проходит тест без таймера либо с ограничением до двух часов.
8. Может обновить страницу и продолжить с сохранёнными ответами.
9. Завершает попытку и получает результат.
10. Не получает доступ к чужим данным.
11. Backend развёрнут в тестовой среде и имеет описанное API.

### Зафиксированные правила

- Банк вопросов — исходная коллекция, например 300 вопросов.
- Quiz — сохранённая подборка, например 50 вопросов, с конкретным порядком.
- Attempt — одно прохождение этого quiz с собственными ответами и временем.
- Повторное прохождение сохранённого quiz создаёт новую попытку, но не новую подборку.
- Для другой случайной подборки пользователь создаёт новый quiz.
- Таймер по умолчанию выключен: time_limit_minutes = 0.
- Положительное ограничение: от 1 до 120 минут.
- Таймер запускается при начале попытки, не при создании quiz.
- Quiz после создания не редактируется в MVP. Можно прочитать, пройти или удалить.
- Questions и options внутри quiz — копии исходных данных.
- Изменение исходного вопроса в банке не изменяет существующий quiz.
- Удаление банка по текущим CASCADE-связям удаляет его quiz и связанные попытки. Это нужно явно указать в интерфейсе удаления.
- Каждый выбранный вариант идентифицируется UUID, а не текстом или буквой A/B/C.
- Импорт не исправляет научную правильность тестов и не удаляет одинаковые варианты.
- Отметка правильного ответа берётся из документа.
- Issues остаётся информационным списком. Новую систему severity, warning/error или обязательное исправление DOCX не вводим.

### Единственное правило оценивания, которое надо решить заранее

Для обычного вопроса с одним отмеченным правильным вариантом всё однозначно: выбран отмеченный вариант — ответ верный.

Для вопроса с нулём или несколькими отмеченными правильными вариантами однозначного ключа в режиме одного ответа нет. Это не повод менять документ или блокировать импорт.

Предлагаемое правило первой версии:

- сохранить и показать такой вопрос как есть;
- не включать его в автоматический балл;
- после завершения показать, что этот вопрос не оценивался;
- считать процент по числу вопросов с однозначным ключом;
- если таких вопросов нет, вернуть процент null, а не делить на ноль.

Это продуктовый выбор, а не готовая ранее согласованная функция. До шага 8.1 либо прими это правило, либо письменно выбери другое. Не позволяй этой неоднозначности случайно превратиться в «первый найденный вариант считается правильным».

### Что остаётся после MVP

- Математические формулы, изображения и сложные таблицы.
- Универсальный PDF-парсер, OCR и сканированные документы.
- AI-проверка документов и генерация вопросов по лекциям.
- Google/Apple login.
- Темы оформления типа cyberpunk. Светлая/тёмная тема — задача frontend.
- Общие банки, совместная работа, публичные ссылки и роли преподавателей.
- Платежи, рейтинги, сложная аналитика, интервальное повторение.
- Очереди, микросервисы, Redis и отдельные workers без подтверждённой необходимости.

Поддержка произвольного PDF не обещается в этой версии. В интерфейсе и README надо честно писать, какие DOCX поддерживаются.

## 2. Календарь и бюджет времени

До 1 февраля осталось примерно 16 недель: около 310–320 часов при 20 часах в неделю. Целевой бюджет backend — около 180 часов задач плюс около 20 часов резерва. Для первого самостоятельного проекта реальные затраты могут оказаться больше.

|---|---|
| 13–25 октября | Quiz создаётся, сохраняется и читается |
| 26 октября – 8 ноября | Начало попытки, сохранение ответов, продолжение после обновления |
| 9–22 ноября | Завершение, серверный таймер, результат и базовая история |

Это ориентиры по результатам, не фиксированные даты для каждого файла. Начать frontend можно, когда API и тестовая среда готовы, даже если некритические улучшения остаются.

### Рекомендуемое распределение 20 часов

- 13 часов — реализация.
- 4 часа — проверки, исправления и небольшие тесты.
- 2 часа — документация по текущей теме.

Если неделю потратил на сложную транзакцию, не пытайся «наверстать» добавлением непроверенного большого куска кода.

## 5. Этап 2: атомарное сохранение quiz

Ориентир: 12 часов.

### Шаг 2.1. Создать repository

Файл: internal/quiz/repository.go.

- [ ] Repository получает существующий pgxpool.Pool.
- [ ] Написать конструктор.
- [ ] Определить Create, который принимает подготовленный Quiz и возвращает сохранённую модель или метаданные.

### Шаг 2.2. Реализовать Create

Порядок:

1. Начать транзакцию.
2. Проверить принадлежность question_bank_id текущему user_id.
3. Вставить quizzes, получить ID и created_at.
4. Пройти по подготовленным вопросам.
5. Вставить quiz_questions, получить новые ID.
6. Для каждого вопроса вставить его quiz_answer_options.
7. Полученные новые ID записать в возвращаемые модели, если они нужны ответу.
8. Выполнить один Commit.
9. При любой ошибке откатить весь пакет.

- [ ] Все SQL внутри операции идут через tx.
- [ ] Сохраняются Text, Position и IsCorrect вариантов.
- [ ] Позиции начинаются с 1.
- [ ] QuestionCount совпадает с реальным количеством сохраняемых вопросов.
- [ ] Проверяется ошибка Commit.
- [ ] Ошибки содержат контекст, но не секреты.

Не использовать ID исходного answer_option как ID скопированного варианта. Эти строки принадлежат разным таблицам и получают новые UUID.

### Шаг 2.3. Написать чтение quiz

Метод: FindByID / FindOwnedByID.

- [ ] Ограничить доступ через quizzes.user_id.
- [ ] Получить метаданные, вопросы и варианты.
- [ ] Вопросы отсортировать по question position.
- [ ] Варианты каждого вопроса — по option position.
- [ ] Проверять ошибки Scan и rows.Err.
- [ ] Закрывать rows.
- [ ] Если применяется JOIN и map для группировки, проверить, что один вопрос не добавляется много раз.

Для списка вопросов в quiz пустой JOIN не должен автоматически превращать существующие метаданные в отсутствие quiz. Хотя Create обязан сохранять непустой состав, способ чтения должен быть понятным.

Готово, когда: подготовленный quiz сохраняется целиком, читается тем же владельцем и недоступен другому.

## 6. Этап 3: создание случайной подборки

Ориентир: 12 часов.

### Шаг 3.1. Собрать зависимости service

Файл: internal/quiz/service.go.

Нужны:

- repository quiz;
- существующий service или repository для чтения вопросов банка с проверкой владельца.

Используй уже работающий ListByBankID. Не пиши второй DOCX-парсер и не делай HTTP-запрос к своему же приложению.

### Шаг 3.2. Проверить CreateRequest

- [ ] bankID имеет корректный UUID.
- [ ] QuestionCount больше нуля.
- [ ] TimeLimitMinutes находится в диапазоне 0–120.
- [ ] Банк принадлежит текущему пользователю.
- [ ] QuestionCount не превышает число имеющихся вопросов.
- [ ] Пустой банк не создаёт пустой quiz.

Если запросили 500 вопросов из банка с 300, вернуть понятную ошибку параметров. Не выбирать с повторениями и не возвращать молча 300 вместо 500.

### Шаг 3.3. Выбрать вопросы

Простой алгоритм MVP:

1. Получить вопросы выбранного банка.
2. Сформировать случайный порядок всей коллекции или индексов.
3. Взять первые N разных элементов.

Для перемешивания подходит math/rand/v2.Shuffle; для выбора индексов — Perm. Для session token продолжает использоваться crypto/rand, а не генератор учебной подборки. Официальная документация: [math/rand/v2 для Go 1.26.5](https://pkg.go.dev/math/rand/v2@go1.26.5).

- [ ] Исходный вопрос выбирается не больше одного раза в пределах одного quiz.
- [ ] Одинаковый текст у разных исходных вопросов не является основанием удалить один из них.
- [ ] Подборка создаётся один раз; GET не выполняет новое перемешивание.
- [ ] Для учебного банка 300–500 вопросов пока достаточно чтения коллекции и выбора в Go.

Оптимизацию для сотен тысяч вопросов можно сделать позднее по измерениям.

### Шаг 3.4. Скопировать и перемешать варианты

## 9. Этап 6: начать и восстановить попытку

Ориентир: 14 часов.

### Шаг 6.1. Реализовать Start

Маршрут: POST /v1/quizzes/{quizID}/attempts.

Порядок:

1. Проверить пользователя и принадлежность quiz.
2. Найти активную попытку этого пользователя для этого quiz.
3. Если она ещё действительна — вернуть её без обновления времени.
4. Если её deadline уже истёк — завершить как expired перед созданием новой.
5. Если действительной попытки нет — создать новую.
6. Для таймера сохранить deadline = started_at + установленное ограничение.
7. Для отсутствия таймера сохранить deadline_at = null.

- [ ] Начало не содержит time_limit или started_at от клиента.
- [ ] Повторный Start не сбрасывает timer.
- [ ] Два одновременных Start не создают две активные попытки.
- [ ] Создание и проверка уникальности выполняются согласованно в транзакции.
- [ ] 201 — новая попытка; 200 — возвращена уже активная.

Вначале можно проверить обычный Start, а повторный Start с истёкшей попыткой закончить после реализации финализации на этапе 8. До этого не считать весь сценарий готовым.

## 10. Этап 7: сохранение ответов

Ориентир: 14 часов.

### Шаг 7.1. Написать SaveAnswer

Маршрут: PUT /v1/attempts/{attemptID}/answers/{quizQuestionID}.
Тело: объект с option_id.

Проверять:

1. Пользователь владеет попыткой.
2. Попытка принадлежит существующему quiz этого пользователя.
3. Указанный quizQuestionID входит именно в этот quiz.
4. Выбранный option_id принадлежит именно этому quizQuestionID.
5. Попытка in_progress.
6. По серверному времени deadline ещё не наступил.

- [ ] Сохранение атомарно: проверка состояния и UPSERT входят в одну транзакцию.
- [ ] Повторная отправка того же выбора безопасна.
- [ ] Изменение выбора обновляет одну строку.
- [ ] Нет сравнения по тексту и буквам.
- [ ] Ответ не сообщает, правильно ли ответил студент.
- [ ] Отсутствующий или чужой ресурс — 404.
- [ ] Уже закрытая или истёкшая попытка — 409.
- [ ] Неверный формат UUID или JSON — 400.

### Шаг 7.2. Согласовать сохранение и Finish

Все операции, меняющие ответы или завершающие одну попытку, должны использовать одну стратегию синхронизации. Практичный вариант — короткая транзакция и блокировка строки попытки через SELECT FOR UPDATE.

Это позволяет последовательно обработать конкурирующие SaveAnswer и Finish. Блокировка строки удерживается до завершения транзакции; подробности: [PostgreSQL 16 — Row-Level Locks](https://www.postgresql.org/docs/16/explicit-locking.html#LOCKING-ROWS).

- [ ] Не держать транзакцию открытой на всё время прохождения.
- [ ] Не ждать действий пользователя внутри транзакции.
- [ ] После получения блокировки снова проверить время и статус.
- [ ] Все изменяющие пути используют эту же блокировку.
- [ ] Завершение не допускает ответа, сохранённого после закрытия.

Если истечение времени фиксируется во время SaveAnswer, продумать, как сохранить статус expired и результат, даже если HTTP-ответ будет 409. Нельзя обновить статус, затем вернуть ошибку и случайно откатить это обновление отложенным Rollback.

Ручные проверки:

- [ ] Сохранить вариант, перечитать попытку.
- [ ] Заменить вариант, убедиться, что строка осталась одна.
- [ ] Передать вариант другого вопроса.
- [ ] Передать вопрос другого quiz.
- [ ] Передать attemptID другого пользователя.
- [ ] Отправить два запроса сохранения.
- [ ] Сохранить ответ после Finish.

Готово, когда: ответы сохраняются и восстанавливаются, а границы владения и связи ресурсов проверяются.

- [ ] Хранить started_at и deadline_at.
- [ ] Проверять deadline на Start, SaveAnswer, GetAttempt, Finish и GetResult.
- [ ] При достижении deadline новые ответы не принимать.
- [ ] Фиксировать expired и результат при следующем обращении к этой попытке.

В базе статус может оставаться in_progress до следующего обращения, но это не должно позволять принимать просроченные ответы. В UI истечение определяется по deadline. Непрерывный серверный cron не обязателен для первой версии.

Граница истечения должна быть одинаковой во всех методах: например server_time >= deadline означает, что время истекло.

HTTP timeout сервера остаётся коротким для отдельного запроса. Не увеличивай WriteTimeout до двух часов из-за продолжительности теста.

- [ ] Повторная отправка imports сейчас добавляет ещё один набор. Это описать; автоматическая дедупликация не является частью текущей версии.
- [ ] На frontend позже не запускать повторную отправку без подтверждения пользователя.
- [ ] Хранение исходного DOCX после успешного preview не обязательно для MVP.

Готово, когда: поддерживаемый DOCX проходит весь путь до quiz, а неподдерживаемый получает понятный ответ без повреждения данных.

## 14. Этап 11: HTTP и безопасность перед публикацией

Ориентир: 16 часов. Эти задачи не означают новую архитектуру приложения.

### Шаг 11.1. Проверить единые ответы

- [ ] Ошибки возвращаются через существующий httpx.
- [ ] Каждый handler заканчивает выполнение после ошибки.
- [ ] 204 не имеет JSON-тела.
- [ ] Создание возвращает 201.
- [ ] Внутренние ошибки логируются, клиент не получает SQL, пароль или путь сервера.
- [ ] Ограничить JSON body; не принимать несколько JSON-объектов как один запрос.
- [ ] Формат ошибки остаётся простым: например существующий объект error с текстом.

Не требуется вводить глобальные severity и сложный каталог error codes.

### Шаг 11.2. Проверить auth

- [ ] Не превращать любую ошибку PostgreSQL в «неправильный пароль».
- [ ] Не раскрывать при login, существует ли конкретный email.
- [ ] Email нормально нормализуется и валидируется.
- [ ] Для bcrypt максимум проверяется в байтах: 72; минимальную длину считать по принятому правилу символов.
- [ ] PasswordHash не попадает в ответы.
- [ ] Session token остаётся криптографически случайным.
- [ ] В БД хранится только token hash.
- [ ] Logout удаляет запись сессии и очищает cookie с тем же именем и Path.
- [ ] Истёкшие сессии не принимаются.
- [ ] Ограничить частоту login/register и дорогого импорта.
- [ ] Сначала достаточно одного экземпляра backend и простого ограниченного rate limiter; внешнюю инфраструктуру добавлять при необходимости.

### Шаг 11.3. Настроить cookie для среды

- [ ] Production использует HTTPS и Secure = true.
- [ ] HttpOnly включён.
- [ ] SameSite выбран осознанно для frontend topology.
- [ ] По умолчанию не выставлять широкий Domain.
- [ ] Срок cookie и серверной сессии согласован.
- [ ] Cookie/token не записываются в логи.

Про cookie-атрибуты и жизненный цикл: [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

### Шаг 11.4. Решить CSRF и CORS

Предпочтительная topology MVP: frontend и API доступны на одном origin; frontend обращается к /v1. Локально можно использовать dev proxy. Это уменьшает настройку cookies и CORS.

- [ ] Для cookie-auth реализовать явную CSRF-защиту изменяющих запросов.
- [ ] Практичный вариант: synchronizer CSRF token, связанный с сессией, и проверяемый заголовок клиента.
- [ ] Для этого варианта добавить к сессии отдельный случайный csrf_token; не использовать session token.
- [ ] Получение: GET /v1/auth/csrf; ответ содержит csrf_token. Проверяемый заголовок: X-CSRF-Token.
- [ ] Описать, где frontend получает token и когда обновляет после login/logout.
- [ ] Для login/register отдельно защитить браузерные изменяющие запросы, например строгой проверкой Origin/Referer по правилам доверенной среды.
- [ ] Проверять Origin/Referer также как дополнительную защиту, не считать наличие CORS универсальной защитой CSRF.
- [ ] SameSite — дополнительная защита, не единственный механизм.
- [ ] Если отдельный origin всё же нужен, разрешать конкретные origins и credentials; не использовать wildcard с credentials.

Конкретный контракт CSRF записать в docs/api.md до подключения frontend. Подробнее: [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

### Шаг 11.5. Проверить ресурсы и наблюдаемость

- [ ] Recovery middleware не допускает падения процесса от panic одного запроса.
- [ ] Логировать method, route/status, duration и request ID, если он есть.
- [ ] Не логировать body с паролями или содержимым документов.
- [ ] Сохранить существующие HTTP timeouts и graceful shutdown.
- [ ] Закрывать pool после завершения активных HTTP-запросов.
- [ ] Есть лёгкий health endpoint.
- [ ] При необходимости добавить ready endpoint с короткой проверкой БД.
- [ ] Использовать context при SQL и прекращать работу при отмене запроса.
- [ ] Реальные секреты не находятся в git; .env.example содержит только placeholders.
- [ ] Если реальный секрет уже попал в публичный git, простого удаления файла недостаточно: его надо заменить в используемой среде.

Готово, когда: приложение можно открыть тестовым студентам без очевидных утечек, обхода авторизации и неограниченной обработки тела.

## 19. Итоговый перечень новых маршрутов

Это предлагаемый контракт; после реализации названия закрепить в документации.

| Method | Path | Результат |
|---|---|---|
| GET | /v1/auth/csrf | CSRF token текущей сессии; 200 |
| POST | /v1/question-banks/{bankID}/quizzes | Создать подборку; 201 |
| GET | /v1/quizzes | Метаданные собственных quiz; 200 |
| GET | /v1/quizzes/{quizID} | Quiz с вопросами без ключа; 200 |
| DELETE | /v1/quizzes/{quizID} | Удалить собственный quiz; 204 |
| POST | /v1/quizzes/{quizID}/attempts | Новая попытка 201 либо действующая 200 |
| GET | /v1/attempts/{attemptID} | Состояние и сохранённые ответы; 200 |
| PUT | /v1/attempts/{attemptID}/answers/{quizQuestionID} | Сохранить/заменить выбранный вариант; 200 |
| POST | /v1/attempts/{attemptID}/finish | Закрыть либо вернуть уже закрытый результат; 200 |
| GET | /v1/attempts/{attemptID}/result | Результат; 200, либо 409 для активной |
| GET | /v1/quizzes/{quizID}/attempts | История собственных попыток; 200 |

Существующие auth, question-bank, question и import routes остаются. Не добавлять дублирующие пути только ради совпадения с этим списком.

### Общие статусы

| Status | Когда использовать |
|---|---|
| 200 | Чтение, сохранение текущего ответа, результат |
| 201 | Создан банк, вопрос, импорт, quiz или новая попытка |
| 204 | Удаление без тела |
| 400 | Неверный JSON/UUID или параметры |
| 401 | Нет действующей сессии |
| 404 | Ресурс отсутствует или недоступен текущему владельцу |
| 409 | Действие конфликтует с состоянием попытки |
| 413 | Превышен размер запроса/файла |
| 415 | Тип файла не поддерживается |
| 422 | Поддерживаемый тип не удалось обработать по содержимому, если выбран такой контракт |
| 429 | Превышена частота запросов |
| 500 | Неожиданная внутренняя ошибка |
| 503 | Готовность сервиса нарушена, например БД недоступна, если реализовано |

Коды 422/415 для parser надо согласовать с уже существующим поведением, а не менять хаотично между endpoints.

## 22. Когда backend действительно закончен

Не «написаны все structs», а выполнены условия:

- [ ] Полный путь от DOCX до результата проходит в staging.
- [ ] Данные одного студента изолированы от другого.
- [ ] Quiz сохраняет состав и порядок.
- [ ] Ответы и время переживают reload и restart.
- [ ] Поздние ответы не принимаются.
- [ ] Завершённый результат не меняется.
- [ ] Авторские ошибки сохраняются как данные, а не исправляются автоматически.
- [ ] Активные ответы API не раскрывают ключи.
- [ ] Лимиты и безопасность браузерного подключения настроены.
- [ ] Критические тесты и CI проходят.
- [ ] Данные имеют backup с проверенным восстановлением.
- [ ] Есть точный API-контракт и инструкция запуска.
- [ ] Ты можешь объяснить путь запроса через handler, service, repository и транзакцию.

С этого момента начинай frontend. Для него уже есть конкретные endpoints и сохранённые состояния, а не только набор backend-файлов.
